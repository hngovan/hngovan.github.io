Review code là một trong những hoạt động dễ bị xem nhẹ trong team phần mềm. Nếu làm hời hợt, nó chỉ còn là bước bấm approve sau khi CI xanh. Nếu làm quá cực đoan, nó biến thành cuộc tranh luận style, kéo dài merge request và làm người gửi code ngại mở PR.

Một review tốt nằm ở giữa hai thái cực đó: đủ kỹ để bảo vệ chất lượng codebase, đủ thực dụng để không chặn tiến độ bằng những góp ý không quan trọng, và đủ tôn trọng để cả reviewer lẫn author đều học được điều gì đó sau mỗi lần review.

## Review code là gì?

Review code là quá trình một hoặc nhiều lập trình viên đọc thay đổi code của người khác trước khi merge vào nhánh chính. Mục tiêu không chỉ là bắt bug. Review còn là nơi kiểm tra thiết kế, độ dễ đọc, test, bảo mật, hiệu năng, khả năng vận hành và mức độ phù hợp với kiến trúc hiện tại.

Trong thực tế, review thường diễn ra qua pull request hoặc merge request. Author gửi thay đổi, reviewer đọc diff, đặt câu hỏi, yêu cầu sửa nếu cần, rồi approve khi thay đổi đủ tốt để vào codebase.

Điểm quan trọng: reviewer không phải người đi tìm lỗi để thắng tranh luận. Reviewer là người chịu trách nhiệm cùng author để codebase tốt lên sau thay đổi đó.

<a id="muc-tieu-that-su-cua-review-code" class="block scroll-mt-31"></a>

## Mục tiêu thật sự của review code

Google Engineering Practices đặt mục tiêu cốt lõi của code review là làm cho sức khỏe tổng thể của codebase tốt lên theo thời gian. Cách hiểu này rất thực dụng: không cần PR nào cũng hoàn hảo tuyệt đối, nhưng mỗi PR được merge nên làm hệ thống tiến lên, không làm nó khó hiểu hơn, mong manh hơn hoặc khó vận hành hơn.

Vậy khi review, câu hỏi chính không phải là:

- "Tôi có viết khác người này không?"
- "Style này có đúng gu của tôi không?"
- "Có thể tối ưu thêm 1% không?"

Câu hỏi chính nên là:

- Thay đổi này có đúng yêu cầu không?
- Nó có phù hợp kiến trúc hiện tại không?
- Người khác có đọc, sửa, debug được không?
- Có test và bằng chứng đủ cho rủi ro của thay đổi không?
- Nó có làm codebase tốt hơn hoặc ít nhất không làm xấu đi không?

## Những thứ nên để tool xử lý trước

Reviewer không nên tốn thời gian bắt lỗi format thủ công nếu repo đã có tool. Những việc có rule khách quan nên tự động hóa:

- Formatter: khoảng trắng, line break, quote style.
- Linter: unused import, pattern nguy hiểm, rule code style.
- Typecheck: lỗi type, field thiếu, contract sai.
- Unit/integration test: logic cốt lõi và case hồi quy.
- Static analysis/security scan: dependency vulnerability, secret scan, rule bảo mật cơ bản.
- CI build: build app, migration check, test command bắt buộc.

Automation không thay thế reviewer, nhưng nó giải phóng reviewer khỏi việc cơ học. Con người nên tập trung vào ý định, thiết kế, rủi ro, sự rõ ràng và những lỗi tool khó hiểu được.

## Quy trình review một pull request

Một quy trình gọn nhưng hiệu quả:

1. Đọc mô tả PR trước khi đọc diff.
2. Xác định mục tiêu: PR này sửa bug gì, thêm feature gì, hoặc refactor phần nào?
3. Nhìn tổng quan file thay đổi để biết phạm vi.
4. Đọc file chính trước, sau đó mới đọc helper/test/style liên quan.
5. Chạy hoặc xem bằng chứng: test, screenshot, log, query plan, migration output.
6. Comment vào rủi ro cụ thể, không comment lan man.
7. Phân biệt comment bắt buộc sửa và góp ý tùy chọn.
8. Approve khi PR đủ tốt, hoặc request changes với lý do rõ.

Với PR lớn, đừng cố review như một khối. Hãy yêu cầu tách nếu có thể:

## Cách review nhanh mà vẫn hiệu quả

Review nhanh không đến từ việc bỏ qua chi tiết quan trọng. Nó đến từ chuẩn bị tốt và giảm kích thước mỗi lần review.

Một số nguyên tắc thực dụng:

- PR nhỏ hơn thì review nhanh hơn.
- Mô tả PR rõ thì reviewer đỡ phải đoán.
- CI xanh trước khi request review.
- Screenshot/video/log/query plan đính kèm nếu thay đổi khó thấy bằng diff.
- Review file chính trước, test sau, rồi mới tới phần phụ.
- Không dành quá lâu cho một lượt review; nếu mệt, dừng lại và quay lại sau.
- Với vấn đề thiết kế lớn, trao đổi trực tiếp rồi chốt lại bằng comment ngắn trong PR.

## Checklist cho author trước khi gửi review

Author chuẩn bị tốt thì reviewer nhanh hơn rất nhiều.

Trước khi request review, nên tự hỏi:

1. PR này có một mục tiêu rõ không?
2. Mô tả PR có nói rõ thay đổi gì, vì sao đổi, cách test không?
3. Có file unrelated, format unrelated hoặc debug log sót lại không?
4. Test/lint/typecheck đã chạy chưa?
5. Có screenshot hoặc video nếu thay đổi UI không?
6. Có query plan nếu thêm query quan trọng không?
7. Có migration note nếu thay đổi schema không?
8. Có rollback plan nếu thay đổi rủi ro cao không?
9. Có đánh dấu phần muốn reviewer nhìn kỹ không?

Một PR tốt không bắt reviewer tự đi tìm ý định của tác giả.

## Khi nào nên approve?

Approve không có nghĩa là "code hoàn hảo". Approve nghĩa là reviewer tin rằng thay đổi này đủ tốt để đi tiếp và làm codebase tốt hơn hoặc không làm nó xấu đi.

Nên approve khi:

- Yêu cầu chính đã đúng.
- Rủi ro lớn đã được xử lý hoặc có kế hoạch rõ.
- Test/bằng chứng phù hợp với mức độ rủi ro.
- Các comment còn lại chỉ là nit hoặc suggestion không chặn.
- Code phù hợp với hướng kiến trúc hiện tại.

Nên request changes khi:

- Có bug correctness rõ.
- Có rủi ro security hoặc data loss.
- API/schema contract bị phá mà không có migration/compatibility plan.
- Query/migration có rủi ro production nhưng không có bằng chứng kiểm tra.
- Thiết kế đi ngược boundary hệ thống và sẽ tạo nợ kỹ thuật rõ ràng.

Điểm khó nhất của review code là cân bằng. Quá dễ dãi thì codebase xuống cấp. Quá cầu toàn thì team bị chậm và review trở thành điểm nghẽn. Một reviewer tốt biết phân biệt đâu là vấn đề phải sửa, đâu là góp ý để sau, và đâu chỉ là sở thích cá nhân.
