Review code không chỉ là bắt lỗi format hoặc hỏi "sao viết thế này?". Một review tốt nên giúp team giảm bug, giữ code dễ đọc, giảm chi phí vận hành và tránh những lỗi chỉ lộ ra khi production có dữ liệu thật.

Tôi thường tách review thành hai lớp: checklist chung cho mọi PR, rồi checklist riêng cho frontend và backend. Bài này là ghi chú thực dụng, không phải quy trình cứng. Với PR nhỏ, chỉ cần quét nhanh; với PR đụng luồng thanh toán, quyền truy cập, query lớn hoặc transaction, review phải kỹ hơn.

## Ví dụ thực tế: review tính năng publish bài viết

Giả sử PR thêm màn publish bài viết trong CMS:

- FE có form nhập tiêu đề, slug, nội dung, tag và trạng thái publish.
- BE có endpoint `POST /posts`.
- Database ghi `posts`, `post_tags` và `audit_logs`.

Một diff nhìn qua có thể "chạy được", nhưng reviewer cần đi theo luồng thật của người dùng:

<DataTable
	headers={['Bước', 'Người dùng/app làm gì', 'Reviewer nên hỏi gì']}
	rows={[
		[
			'1',
			'User để trống title, nhập slug trùng, hoặc chọn tag không tồn tại',
			'FE chỉ disable button hay BE cũng validate? Error message trả về có rõ không?'
		],
		[
			'2',
			'User bấm publish hai lần do mạng chậm',
			'Endpoint có guard duplicate slug hoặc unique constraint phù hợp không?'
		],
		[
			'3',
			'BE tạo post rồi gắn tag và ghi audit log',
			'Các thay đổi có nằm trong cùng transaction DB không? Nếu ghi tag fail thì rollback thế nào?'
		],
		[
			'4',
			'FE gọi API xong refetch danh sách bài viết',
			'Có tạo N+1 query hoặc refetch quá nhiều endpoint không? Loading/error state có đúng không?'
		],
		[
			'5',
			'Hệ thống ghi log lỗi',
			'Log có lộ token, nội dung nháp nhạy cảm, hoặc thông tin không nên ghi không?'
		]
	]}
/>

Ví dụ review comment có bằng chứng:

```txt
Endpoint POST /posts đang cho phép tạo trùng slug nếu user bấm publish hai lần rất nhanh.
Nên thêm unique constraint cho slug active và xử lý lỗi duplicate thành message rõ cho FE.
```

Ví dụ review FE:

```txt
Form đang dùng if (title) nhưng không trim trước khi submit.
Title toàn khoảng trắng vẫn qua được UI, sau đó BE mới trả lỗi.
Nên normalize input ở FE để feedback nhanh hơn, nhưng BE vẫn phải validate lại.
```

Ví dụ review query:

```txt
Màn danh sách bài viết gọi /posts rồi mỗi item gọi /authors/:id và /tags?post_id=...
Với 50 bài sẽ thành hơn 100 request/query. Nên trả đủ author/tag summary từ API list hoặc batch theo ids.
```

Các comment kiểu này dễ xử lý hơn nhiều so với "đoạn này có vẻ không ổn", vì nó chỉ ra kịch bản lỗi, tác động và hướng sửa.

ESLint là lớp kiểm tra cơ bản cho JavaScript/TypeScript. Tài liệu ESLint mô tả nó là công cụ tìm và sửa vấn đề trong code JavaScript: https://eslint.org/docs/latest/. Nhưng lint/typecheck chỉ là cửa đầu. PR pass lint vẫn có thể sai nghiệp vụ, query chậm, transaction sai hoặc render UI tệ trên mobile.

## Review database query

Nếu PR thêm hoặc sửa query, chỉ nhìn SQL text là chưa đủ. Cần xem plan và dữ liệu thực tế gần production.

PostgreSQL `EXPLAIN` cho biết execution plan, scan type, join algorithm và estimate; `ANALYZE` thực thi query để lấy runtime thật: https://www.postgresql.org/docs/current/sql-explain.html. MySQL `EXPLAIN` cũng mô tả cách statement được execute, và `EXPLAIN ANALYZE` chạy statement rồi trả thêm timing/iterator information: https://dev.mysql.com/doc/refman/8.4/en/explain.html

## Review memory và tài nguyên

Memory bug thường không lộ trong test nhỏ. Một đoạn code đọc file, export CSV, aggregate report hoặc gọi API batch có thể pass local nhưng gây OOM khi dữ liệu thật lớn.

Các câu hỏi nên hỏi:

- Có đang load toàn bộ table/file vào array không?
- Có thể streaming, cursor, pagination hoặc chunking không?
- Có giữ buffer lớn trong closure/cache không giới hạn không?
- Có timeout/cancel khi downstream chậm không?
- Có retry không giới hạn làm nhân đôi memory/network không?

Ở FE, memory leak hay đến từ event listener/subscription/timer không cleanup, object URL không revoke, cache không có limit. Ở BE, leak thường đến từ global cache, queue in-memory, giữ request payload lớn, hoặc ORM load quan hệ quá rộng.

<a id="review-transaction-va-consistency" class="block scroll-mt-31"></a>

## Review transaction và consistency

Transaction không chỉ là bọc `BEGIN/COMMIT`. Cần review phạm vi transaction, isolation, retry và side effect.

Ví dụ flow xấu:

```ts
await db.transaction(async tx => {
	await tx.order.create(...)
	await paymentGateway.charge(...)
	await tx.payment.create(...)
})
```

Gọi payment gateway trong transaction làm transaction giữ lock lâu, và nếu rollback sau khi charge thành công thì hệ thống rơi vào trạng thái khó bù. Flow tốt hơn thường là tách side effect ra khỏi transaction DB, dùng outbox/idempotency hoặc state machine tùy domain.

Về visibility, PostgreSQL docs giải thích ở `READ COMMITTED`, query chỉ thấy dữ liệu đã commit trước khi query bắt đầu: https://www.postgresql.org/docs/current/transaction-iso.html. MySQL InnoDB docs giải thích isolation levels và consistent reads trong InnoDB: https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html. Khi review bug "trong transaction thấy row mới, ngoài transaction chưa thấy", đó thường là behavior đúng cho dữ liệu chưa commit, không phải database lỗi.

## Câu hỏi nên để lại khi review

Review comment nên cụ thể và có bằng chứng. Một số câu hỏi tôi hay dùng:

- "Query này đã chạy `EXPLAIN ANALYZE` với dữ liệu gần production chưa?"
- "Đoạn này có thể tạo N+1 query khi danh sách có 50 item không?"
- "Nếu request bị retry sau timeout, có tạo duplicate record không?"
- "Field này có thể là `0` hoặc `null` không? Nếu có thì điều kiện `if (value)` có đúng không?"
- "Transaction này có cần bao cả API call bên ngoài không?"
- "Có test case cho permission khác tenant/user khác chưa?"
- "Trên mobile/tablet text dài trong button/table có vỡ layout không?"

Comment tốt nên nói rõ rủi ro và gợi ý hướng sửa. Nếu chưa chắc, hỏi bằng câu hỏi có ngữ cảnh thay vì chặn PR bằng nhận định mơ hồ.
