Khi chọn database cho một service mới, câu hỏi hay gặp không phải là "PostgreSQL mạnh hơn hay MySQL nhanh hơn?", mà là: dữ liệu của mình đọc nhiều hay ghi nhiều, query đơn giản hay phức tạp, team quen vận hành hệ nào, sau này có cần report, JSON, search, geospatial, partitioning hay migration phức tạp không?

PostgreSQL và MySQL đều là RDBMS phổ biến, đều dùng SQL, đều đủ tốt cho rất nhiều web app. Nhưng cách mỗi hệ ưu tiên thiết kế khác nhau. MySQL thường hợp với service web đơn giản, lấy một lượng dữ liệu nhất định để hiển thị, còn PostgreSQL nổi bật khi cần nhiều tính năng, phân tích và query phức tạp. AWS cũng đưa ra hướng chọn tương tự: PostgreSQL hợp hơn với ứng dụng enterprise có thao tác ghi thường xuyên và query phức tạp; MySQL phù hợp khi prototype, app nội bộ ít người dùng, hoặc kho thông tin đọc nhiều và cập nhật không thường xuyên.

Bài này viết lại theo hướng thực dụng hơn: nhìn vào từng loại service, từng loại query và từng rủi ro vận hành để quyết định.

## 1. Chọn theo workload trước, đừng chọn theo cảm tính

Một lỗi phổ biến là chọn database theo danh tiếng: "PostgreSQL xịn hơn" hoặc "MySQL nhanh hơn". Cách này nguy hiểm vì hiệu năng database phụ thuộc workload cụ thể.

Ví dụ một service catalog sản phẩm có đặc điểm:

- Mỗi ngày chỉ import thêm vài nghìn sản phẩm.
- 99% request là đọc danh sách, lọc theo category, lấy top sản phẩm mới.
- Query chủ yếu là `WHERE category_id = ? ORDER BY created_at DESC LIMIT 20`.
- Team đã có backup, monitoring, read replica MySQL.

Với bài toán này, MySQL là lựa chọn rất thực dụng. Không phải vì PostgreSQL kém, mà vì workload đơn giản, đọc nhiều, query rõ index và team đã có năng lực vận hành MySQL.

Ngược lại, một service quản lý đơn hàng B2B có đặc điểm:

- Có nhiều trạng thái đơn hàng, audit log, rule duyệt nhiều bước.
- Report theo tháng, khách hàng, vùng, nhân viên, trạng thái.
- Query thường JOIN nhiều bảng, dùng aggregate, window function, JSON field, filter động.
- Cần constraint rõ để tránh dữ liệu sai.

Với bài toán này, PostgreSQL thường đáng cân nhắc hơn. Database không còn chỉ là nơi lưu record để lấy ra theo id; nó tham gia nhiều hơn vào tính đúng và khả năng phân tích dữ liệu.

AWS viết rằng PostgreSQL phù hợp hơn cho ứng dụng cấp doanh nghiệp có thao tác ghi thường xuyên và truy vấn phức tạp, trong khi MySQL có thể phù hợp cho prototype, app nội bộ ít người dùng hoặc kho thông tin có nhiều thao tác đọc hơn và cập nhật không thường xuyên. Đây là cách nhìn nên dùng khi chọn DB: bắt đầu từ đặc tính service.

## 2. Query đơn giản và query phức tạp

Một điểm rất đáng nhớ: SELECT đơn giản thì MySQL và PostgreSQL thường không khác biệt nhiều. Khác biệt rõ hơn khi query phải sort lượng dữ liệu lớn, JOIN nhiều hoặc cần thuật toán query phức tạp.

Ví dụ service timeline:

```sql
SELECT id, body, created_at
FROM posts
WHERE user_id = 10
ORDER BY created_at DESC
LIMIT 20;
```

Nếu có index phù hợp như `(user_id, created_at DESC)`, cả MySQL và PostgreSQL đều có thể xử lý tốt. Đây là nhóm query mà MySQL rất hay được dùng trong web app: lấy một tập nhỏ, có điều kiện rõ, trả về nhanh.

Nhưng với report doanh thu theo từng khách hàng, so sánh kỳ hiện tại với kỳ trước, query có thể bắt đầu giống thế này:

```sql
WITH monthly_revenue AS (
	SELECT
		customer_id,
		date_trunc('month', paid_at) AS month,
		sum(total_amount) AS revenue
	FROM invoices
	WHERE paid_at >= now() - interval '12 months'
	GROUP BY customer_id, date_trunc('month', paid_at)
)
SELECT
	customer_id,
	month,
	revenue,
	revenue - lag(revenue) OVER (
		PARTITION BY customer_id
		ORDER BY month
	) AS diff_from_previous_month
FROM monthly_revenue;
```

Loại query này là nơi PostgreSQL thường dễ chịu hơn: CTE, window functions, expression index, partial index, materialized view và planner linh hoạt giúp ta giữ logic gần dữ liệu. MySQL 8 cũng đã có CTE và window functions, nhưng khi hệ thống dựa nhiều vào query phân tích, vẫn nên benchmark kỹ với data thật.

Khi review một pull request có query mới, đừng chỉ hỏi "đã thêm index chưa". Hãy chạy `EXPLAIN` hoặc `EXPLAIN ANALYZE` với dữ liệu gần production. PostgreSQL documentation mô tả planner/optimizer là phần chọn plan được ước tính nhanh nhất trong nhiều cách chạy query; tài liệu `EXPLAIN` cho biết plan đang scan table thế nào, join thế nào. MySQL cũng có `EXPLAIN` và `EXPLAIN ANALYZE` để xem cách MySQL execute statement.

## 3. Index và kiểu dữ liệu

AWS tóm tắt một điểm quan trọng: PostgreSQL là hệ quản trị cơ sở dữ liệu quan hệ đối tượng và có nhiều lựa chọn kiểu dữ liệu hơn, trong khi MySQL là hệ quản trị quan hệ rất phổ biến cho web app. AWS cũng nêu PostgreSQL có các loại index như expression index, partial index và hash index; MySQL hỗ trợ B-tree và R-tree.

Trong dự án thật, sự khác biệt này hiện ra ở các case như:

- Cần index riêng cho `WHERE deleted_at IS NULL`.
- Cần index trên biểu thức như `lower(email)`.
- Cần query JSON nhưng vẫn muốn index vào một field trong JSON.
- Cần dữ liệu geospatial như bản đồ, khoảng cách, vùng phủ.
- Cần range type, array, enum, network address.

PostgreSQL thường cho nhiều công cụ hơn để mô hình hóa những case này. Ví dụ:

```sql
CREATE UNIQUE INDEX users_email_unique_active
ON users (lower(email))
WHERE deleted_at IS NULL;
```

Index này nói rõ business rule: email active không được trùng, nhưng user đã soft-delete thì không còn chặn email mới. Trong PostgreSQL, partial index là công cụ rất tiện cho kiểu rule này.

MySQL vẫn có thể giải quyết nhiều bài toán tương tự bằng generated column, composite index, constraint ở application hoặc thiết kế schema khác. Nhưng nếu domain của bạn có nhiều rule dữ liệu đặc thù, PostgreSQL thường giúp biểu diễn rule trực tiếp trong database rõ hơn.

## 4. Transaction, MVCC và dữ liệu nhìn thấy

Hãy dùng ví dụ gần web app: một admin tạo bài viết mới trong CMS.

Ban đầu bảng `posts` có id `1`, `2`.

Session A mở transaction để tạo bài viết id `3`:

```sql
BEGIN;

INSERT INTO posts (id, title, status)
VALUES (3, 'PostgreSQL vs MySQL', 'draft');

SELECT id FROM posts ORDER BY id;
-- Session A thấy: 1, 2, 3
```

Trong lúc Session A chưa `COMMIT`, Session B ở ngoài transaction query cùng bảng:

```sql
SELECT id FROM posts ORDER BY id;
-- Session B thấy: 1, 2
```

Sau khi Session A commit:

```sql
COMMIT;
```

Session B chạy query mới thì mới thấy id `3`.

Điểm này giống về mặt khái niệm ở cả PostgreSQL và MySQL/InnoDB: transaction chưa commit thì session khác không được thấy dữ liệu uncommitted. Khác biệt nằm ở snapshot và isolation mặc định.

Khi debug bug "sao trong transaction không thấy row mới", đừng chỉ nhìn SQL text. Hãy nhìn isolation level và transaction boundary.

## 5. UPDATE, DELETE, VACUUM và purge

Đây là phần nhiều người bỏ qua khi mới dùng database: xóa một row không có nghĩa là file table lập tức nhỏ lại.

Trong PostgreSQL, do MVCC, `UPDATE` thường giống tạo version mới của row. Version cũ không còn visible với transaction mới, nhưng vẫn có thể cần cho transaction cũ đang giữ snapshot. Vì vậy PostgreSQL cần `VACUUM` để dọn dead row versions. Tài liệu PostgreSQL về routine vacuuming nói `VACUUM` chuẩn remove dead row versions trong table và index, đánh dấu space có thể tái sử dụng, nhưng thường không trả space về hệ điều hành trừ một số trường hợp cuối file table trống. `VACUUM FULL` có thể compact mạnh hơn bằng cách rewrite table, nhưng nặng và không nên xem là thao tác nhẹ.

Trong MySQL InnoDB, tài liệu InnoDB multi-versioning nói record đã delete-mark không bị remove vật lý ngay; nó được purge khi undo log record liên quan không còn cần cho MVCC hoặc rollback. Nói cách khác, MySQL cũng có bài toán "dọn version cũ", chỉ là cơ chế và thuật ngữ khác PostgreSQL.

Ví dụ thực tế: hệ thống audit log hoặc notification.

Nếu mỗi ngày insert 10 triệu notification, sau 30 ngày chạy job xóa notification cũ:

```sql
DELETE FROM notifications
WHERE created_at < now() - interval '30 days';
```

Query này nhìn đơn giản nhưng có thể gây áp lực lớn:

- PostgreSQL: dead tuples tăng mạnh, autovacuum phải dọn, table/index có thể bloat.
- MySQL: purge phải xử lý bản ghi đã delete-marked và undo/history liên quan.
- Cả hai: nếu có transaction đọc cũ mở quá lâu, việc dọn rác bị ảnh hưởng.

Trong case kiểu này, giải pháp tốt hơn thường là partition theo ngày/tháng rồi drop partition cũ, thay vì delete từng row khổng lồ.

## 6. DDL, migration và vận hành production

DDL là nỗi đau rất thật khi database đã chạy production. Thêm cột, đổi type, thêm index, đổi constraint, rename column: ở local thì nhanh, lên bảng vài trăm triệu row thì có thể lock hoặc làm chậm service.

MySQL, đặc biệt các phiên bản mới với InnoDB, có nhiều cải thiện cho online DDL. Một số thao tác có thể chạy ít block hơn, nhưng không phải mọi migration đều an toàn. PostgreSQL cũng có nhiều thao tác DDL nhanh, nhưng vẫn có thao tác cần lock mạnh hoặc rewrite table tùy loại thay đổi.

Vì vậy rule thực tế không phải là "DB nào migration không lock", mà là:

- Đọc documentation của đúng version đang chạy.
- Test migration trên data gần production.
- Đo lock time, runtime, disk usage.
- Với index lớn, ưu tiên cách build concurrent/online nếu database hỗ trợ.
- Với thay đổi lớn, dùng chiến lược expand-contract: thêm cột mới, dual-write, backfill nhỏ, switch read, rồi cleanup.

Ví dụ migration nên tránh làm vội:

```sql
ALTER TABLE orders
ALTER COLUMN metadata TYPE jsonb
USING metadata::jsonb;
```

Nếu bảng lớn, đây không chỉ là câu SQL. Đây là một kế hoạch vận hành: chạy lúc nào, lock bao lâu, rollback thế nào, monitor gì, app có chịu được schema song song không.

## 7. Replication, backup và hệ sinh thái

Database không sống một mình. Khi service lớn dần, bạn sẽ cần backup, restore drill, read replica, failover, monitoring, migration tool, schema diff, connection pool và cách debug slow query.

MySQL có lợi thế rất lớn về độ phổ biến trong web hosting và LAMP stack. Nhiều team đã có kinh nghiệm vận hành MySQL, nhiều managed service hỗ trợ tốt, nhiều framework mặc định hoạt động mượt với MySQL.

PostgreSQL có hệ sinh thái extension mạnh: PostGIS cho geospatial, full-text search, JSONB, materialized view, foreign data wrapper, logical replication và nhiều kiểu index. Nếu service có nhu cầu mở rộng domain logic trong database, PostgreSQL thường cho nhiều đường đi hơn.

AWS nhắc cả Amazon RDS và Aurora đều hỗ trợ MySQL/PostgreSQL, nên nếu chạy managed cloud, lựa chọn không còn chỉ là database engine mà còn là operational model: ai backup, ai patch, ai monitor, ai xử lý failover.

## Checklist trước khi quyết định

Trước khi chốt PostgreSQL hay MySQL, tôi sẽ trả lời các câu này:

1. 80% query quan trọng nhất là gì? Có query mẫu chưa?
2. Service đọc nhiều hay ghi nhiều? Tỷ lệ read/write ước lượng là bao nhiêu?
3. Có report, aggregate, JOIN lớn, window function, CTE không?
4. Có cần JSONB, PostGIS, partial index, expression index, materialized view không?
5. Có nhiều delete/update hàng loạt không? Nếu có, chiến lược vacuum/purge/partition là gì?
6. Transaction có mở lâu không? Có job/background worker nào giữ transaction trong lúc gọi API ngoài không?
7. Team đang quen backup/restore/replication/monitoring hệ nào?
8. Migration production sẽ chạy bằng tool nào? Có đo lock và rollback plan chưa?
9. Nếu dùng managed cloud, RDS/Aurora/Supabase/Cloud SQL hỗ trợ operational requirement nào tốt hơn?

Nếu trả lời xong mà mọi thứ vẫn ngang nhau, hãy chọn hệ mà team vận hành tự tin hơn. Database đúng về lý thuyết nhưng team không backup/restore/debug được thì vẫn là lựa chọn rủi ro.
