## Ví dụ thực tế: danh sách bài viết mới

Hãy tưởng tượng màn danh sách bài viết trong CMS. Người dùng mở danh sách bài mới nhất, mỗi lần lấy 5 dòng:

		['1', '105', '10:05:00', 'PostgreSQL vs MySQL'],

		['5', '101', '10:01:00', 'Đọc EXPLAIN ANALYZE']
	]}

Nếu dùng `OFFSET/LIMIT`, trang 2 sẽ là "bỏ qua 5 dòng đầu, lấy 5 dòng tiếp theo". Vấn đề xảy ra khi giữa lúc người dùng đang đọc trang 1, editor publish một bài mới `106` chen lên đầu danh sách. Khi người dùng bấm sang trang 2, database lại bỏ qua 5 dòng đầu của danh sách mới, nên bài `101` có thể bị lặp hoặc một bài cũ bị bỏ qua tùy dữ liệu thay đổi.

Minh họa timeline:

			'Trang 2 bắt đầu từ 101, bị lặp với trang 1'
		]

Với keyset pagination, trang tiếp theo không nói "bỏ qua 5 dòng" nữa, mà nói "lấy các bài cũ hơn bài cuối tôi đã thấy", ví dụ cursor là `(created_at = 10:01:00, post_id = 101)`. Khi đó bài mới `106` chen lên đầu không làm trang tiếp theo bị lệch.

```sql
SELECT post_id, title, created_at, author_id
FROM posts
WHERE (created_at, post_id) < ('2026-07-29 10:01:00', 101)
ORDER BY created_at DESC, post_id DESC
LIMIT 5;
```

Đây là lý do các màn dạng feed, inbox, audit log, danh sách bài viết hoặc lịch sử đơn hàng thường hợp với cursor/keyset hơn page number truyền thống.

## OFFSET/LIMIT: cách dễ hiểu nhất

Đây là cách phân trang quen thuộc nhất trong PostgreSQL, MySQL hoặc SQLite:

```sql
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC
LIMIT 20 OFFSET 40;
```

Nếu mỗi trang có 20 bản ghi, `OFFSET 40` nghĩa là bỏ qua 40 bản ghi đầu và lấy 20 bản ghi tiếp theo. Với SQL Server hoặc Oracle mới hơn, cú pháp thường là:

```sql
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC
OFFSET 40 ROWS
FETCH NEXT 20 ROWS ONLY;
```

Ưu điểm của cách này là đơn giản, dễ map với UI có số trang và hỗ trợ nhảy thẳng đến một trang bất kỳ. Với bảng nhỏ, trang quản trị nội bộ hoặc dữ liệu không tăng quá nhanh, đây vẫn là lựa chọn thực dụng.

### Khi OFFSET/LIMIT hợp lý

- Dữ liệu vừa phải và số trang sâu ít được truy cập.
- Người dùng cần nhảy đến trang 12, 50 hoặc 200.
- UI cần hiển thị tổng số trang rõ ràng.
- Query phục vụ màn admin, báo cáo nội bộ hoặc dữ liệu đã lọc hẹp.

<a id="van-de-cua-offset-o-trang-sau" class="block scroll-mt-31"></a>

## Vấn đề của OFFSET ở trang sâu

Điểm dễ nhầm là database không "nhảy cóc" miễn phí tới vị trí offset. Để trả về trang sâu, database vẫn phải xác định thứ tự dữ liệu, đi qua các bản ghi bị bỏ qua, rồi mới lấy phần cần trả về.

Ví dụ:

```sql
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC
LIMIT 20 OFFSET 200000;
```

Query này chỉ trả về 20 dòng, nhưng database vẫn phải xử lý một lượng lớn dòng trước đó. Càng đi sâu, chi phí càng tăng.

### Vấn đề nhất quán dữ liệu

`OFFSET` cũng dễ tạo trải nghiệm lặp hoặc thiếu bản ghi nếu dữ liệu thay đổi giữa hai lần request.

Giả sử người dùng vừa đọc trang 1, sau đó có vài bản ghi mới được insert lên đầu danh sách. Khi người dùng sang trang 2, một số bản ghi cuối của trang 1 có thể bị đẩy xuống và xuất hiện lại. Ngược lại, nếu có bản ghi bị xóa, một vài dòng có thể bị bỏ qua.

Vấn đề này không phải lúc nào cũng nghiêm trọng. Với dashboard nội bộ, đôi khi chấp nhận được. Với feed, log sự kiện, timeline hoặc API public, nó đáng để xử lý kỹ hơn.

## Keyset pagination: đi tiếp từ bản ghi cuối

Keyset pagination, còn gọi là cursor pagination hoặc seek method, không yêu cầu database bỏ qua N bản ghi. Thay vào đó, request tiếp theo gửi lại mốc cuối cùng của trang trước.

Trang đầu:

```sql
SELECT id, title, created_at
FROM articles
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Trang tiếp theo:

```sql
SELECT id, title, created_at
FROM articles
WHERE (created_at, id) < ('2026-07-29 10:30:00', 12045)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Nếu có index phù hợp, database có thể bắt đầu gần đúng vị trí trong index rồi đọc tiếp 20 dòng. Vì vậy chi phí thường ổn định hơn nhiều khi dữ liệu lớn.

### Vì sao cần thêm id vào ORDER BY?

Nếu chỉ sort theo `created_at`, nhiều bản ghi có thể trùng thời điểm. Khi đó cursor chỉ chứa `created_at` sẽ không đủ để biết bản ghi nào đã đọc và bản ghi nào chưa đọc.

Cách phổ biến là thêm một cột duy nhất để phá hòa:

```sql
ORDER BY created_at DESC, id DESC
```

Cursor lúc này gồm cả `created_at` và `id`. Điều kiện tuple:

```sql
WHERE (created_at, id) < (:last_created_at, :last_id)
```

có thể hiểu là: lấy các bản ghi đứng sau cặp giá trị cuối cùng theo đúng thứ tự sort.

### Khi database không hỗ trợ tuple comparison

Một số database hoặc phiên bản cũ không dùng được cú pháp `(a, b) < (?, ?)`. Khi đó viết tường minh:

```sql
WHERE created_at < :last_created_at
   OR (created_at = :last_created_at AND id < :last_id)
```

Điều quan trọng là điều kiện `WHERE` phải khớp với `ORDER BY`. Nếu đổi chiều sort hoặc đổi cột sort, cursor cũ không còn ý nghĩa và nên reset về trang đầu.

<a id="cursor-nen-chua-gi" class="block scroll-mt-31"></a>

## Cursor nên chứa gì?

Cursor không nhất thiết chỉ là `last_id`. Với danh sách sort theo `id ASC`, `last_id` là đủ:

```sql
SELECT id, name
FROM customers
WHERE id > :last_id
ORDER BY id ASC
LIMIT 50;
```

Nhưng với danh sách sort theo `created_at DESC, id DESC`, cursor nên chứa cả hai giá trị:

```json
{
	"created_at": "2026-07-29T10:30:00Z",
	"id": 12045
}
```

Trong API thực tế, có thể mã hóa cursor thành chuỗi opaque để client không phụ thuộc vào cấu trúc bên trong. Server vẫn giải mã được để dựng điều kiện SQL.

### Nhược điểm của keyset

Keyset không phù hợp với mọi UI. Người dùng thường chỉ đi tiếp/lùi tuần tự, khó nhảy thẳng đến trang bất kỳ. Tổng số trang cũng không còn tự nhiên như mô hình page number.

Vì vậy keyset hợp với:

- Feed, activity log, inbox, danh sách event.
- API cần hiệu năng ổn định khi dữ liệu lớn.
- UI dạng "Tải thêm" hoặc infinite scroll.
- Bảng thay đổi liên tục và không muốn lặp/mất dòng giữa các trang.

## Window functions và ROW_NUMBER

Một cách khác là đánh số dòng bằng `ROW_NUMBER()` rồi lọc theo khoảng:

```sql
WITH numbered AS (
	SELECT
		id,
		title,
		created_at,
		ROW_NUMBER() OVER (ORDER BY created_at DESC) AS row_index
	FROM articles
)
SELECT id, title, created_at
FROM numbered
WHERE row_index BETWEEN 41 AND 60;
```

Cách này hữu ích khi cần duy trì code cũ, làm việc với database/cú pháp cũ, hoặc cần phân trang theo nhóm. Nhưng với phân trang thông thường, nó thường không nhanh hơn `OFFSET/LIMIT`, vì database vẫn cần đánh số trên tập kết quả trước khi lọc.

### Trường hợp window functions thật sự sáng giá

Window functions mạnh khi bài toán không chỉ là "lấy trang N". Ví dụ lấy top 3 sản phẩm theo doanh số trong từng danh mục:

```sql
SELECT category, product_name, sales
FROM (
	SELECT
		category,
		product_name,
		sales,
		DENSE_RANK() OVER (
			PARTITION BY category
			ORDER BY sales DESC
		) AS rank_in_category
	FROM products
) ranked
WHERE rank_in_category <= 3;
```

Ở đây `PARTITION BY` chia dữ liệu theo nhóm, còn `ORDER BY` xác định thứ tự trong từng nhóm. Đây là dạng bài toán mà `OFFSET/LIMIT` không diễn đạt gọn bằng.

<a id="count-cung-la-mot-diem-nghen" class="block scroll-mt-31"></a>

## COUNT(\*) cũng là một điểm nghẽn

Ngay cả khi query lấy dữ liệu đã tối ưu, phần đếm tổng số dòng vẫn có thể chậm:

```sql
SELECT COUNT(*)
FROM articles
WHERE status = 'published';
```

Với bảng lớn, database có thể phải đọc rất nhiều dữ liệu để trả về con số chính xác. Nếu UI luôn cần "trang 5 / 10.432", chi phí `COUNT(*)` có thể trở thành vấn đề riêng.

Một vài hướng xử lý:

- Bỏ tổng số trang, chỉ hiển thị "Trước" và "Sau".
- Dùng "Load more" thay vì page number.
- Cache tổng số theo điều kiện lọc phổ biến.
- Hiển thị mốc gần đúng như `1000+` nếu sản phẩm cho phép.

## Checklist khi triển khai

1. Luôn có `ORDER BY` rõ ràng. Không có thứ tự ổn định thì phân trang không đáng tin.
2. Sort theo cột có index. Với keyset, cân nhắc composite index đúng thứ tự, ví dụ `(created_at, id)`.
3. Thêm cột unique để phá hòa khi sort theo cột có thể trùng.
4. Giới hạn `limit` từ phía server, ví dụ tối đa 50 hoặc 100.
5. Reset cursor khi user đổi filter, đổi sort field hoặc đổi sort direction.
6. Test với dữ liệu đủ lớn, không chỉ vài nghìn dòng dev.
7. Đừng mặc định cần `COUNT(*)` chính xác nếu UI không thật sự cần.
